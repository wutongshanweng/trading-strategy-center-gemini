## 1. 使用说明

### 1.1 给专家评审模型

请先完整阅读本文件，再阅读本文件第 3.3 节列出的仓库证据。你的任务不是直接生成大量代码，而是：

1. 验证本文件对现状的判断，逐条指出证据、误判和遗漏。
2. 对升级项做删减、补强和重新排序，优先提升可信度、可维护性和可运营性。
3. 为每个保留项输出可实施设计：边界、接口、数据模型、迁移、测试、监控、回滚和验收。
4. 识别量化研究中的数据泄漏、幸存者偏差、未来函数、过拟合、交易成本低估和不可复现问题。
5. 不要为了体现能力而引入微服务、Kubernetes、Kafka、全新数据库或新 ML 模型；除非有可量化收益和迁移理由。
6. 所有结论必须标注为以下三类之一：
   - `VERIFIED`：由代码、测试或运行结果直接验证；
   - `REPO-CLAIMED`：由仓库文档或历史记录声明，但本轮未重新运行；
   - `PROPOSED`：建议或待实现内容。

### 1.2 给后续 GPT 实施模型

1. 一次只实施一个 Phase，禁止一次性跨阶段重构。
2. 每个 Phase 开始前先提交设计说明、涉及文件和验收命令，得到确认后再编码。
3. 先写失败测试或验收脚本，再做最小实现；每个行为变化必须有回归测试。
4. 不得修改未列入当前 Phase 的模块，不得顺手清理无关代码。
5. 不得连接真实券商、CTP 或任何实盘下单接口。
6. 不得弱化人工审批、风险阻断、成本模型和可审计记录。
7. 每个 Phase 完成后必须提供：变更摘要、测试证据、迁移步骤、回滚方法、遗留风险和文档更新。

## 2. 项目目标与不可突破边界

### 2.1 产品定位

这是一个面向个人/小团队的全栈量化研究与决策平台，主要飞轮为：

```text
多源市场数据
  → 数据质量与点时特征
  → 规则策略 / Alpha 因子 / ML / 缠论 / 宏观新闻
  → 多 Agent 研究与综合判断
  → 可信回测、压力测试与成本评估
  → 信号质量分级、模拟成交与结果回填
  → 策略生命周期、锦标赛与人工晋升
```

升级目标不是增加更多表面功能，而是把现有能力升级为：

- **研究可信**：任何信号和回测都能回答“用了什么数据、什么版本、是否点时、成本如何、能否复现”。
- **运行可靠**：数据任务、Agent 任务、模拟成交和数据库迁移可监控、可恢复、可回滚。
- **风险可控**：系统保持研究/模拟属性，所有高风险动作有人审、额度、熔断和审计。
- **开发可持续**：文档与实现一致，CI 能阻止回归，新设备可复现安装和验证。
- **决策可解释**：建议必须关联证据、反证、置信度、阻断原因和事后结果。

### 2.2 硬性边界

以下边界除非用户另行书面确认，不得改变：

1. **不接实盘执行**：允许模拟交易和只读研究，不实现真实资金自动交易。
2. **Champion 晋升必须人工批准**：Agent 或定时任务不得绕过人工审批。
3. **交易门禁失败即阻断**：数据质量、风险、成本、流动性、证据完整性任一关键门禁失败，不得标记为可交易。
4. **LLM 不是事实源**：LLM 只能归纳、解释和提出研究假设，不能凭空生成行情、财务数据或交易执行结果。
5. **密钥不入库、不入日志、不入文档**：仓库是私有不代表凭据可以提交。当前本机 Git 远程凭据由用户明确选择保留，但任何模型不得输出、复制或写入该 Token。
6. **PostgreSQL 是统一事实仓库**：不得无设计依据引入第二套持久化真相源。
7. **破坏性数据库操作必须有备份、演练和显式批准**。

## Phase 1：研究可复现与数据血缘（P0）

### 目标

让每个回测、信号和 Agent 建议都能被重放和审计。

### 设计与实施

1. 定义统一 `ResearchRun`：`run_id`、代码 SHA、配置哈希、数据快照/最大可见时间、标的集合、时间范围、随机种子、依赖版本、状态和父运行。
2. 定义 `DatasetSnapshot` 或等价血缘：源、抓取时间、事件时间、修订时间、质量状态、行数、内容/分区哈希。
3. 因子、回测、信号、Agent 任务、模拟订单统一关联 `run_id` 和 evidence IDs。
4. 对宏观、财务和新闻明确 `event_time`、`available_time`、`revised_at`，查询必须使用当时可见版本。
5. 建立可重放命令：给定 `run_id`，输出差异报告；浮点容差必须按指标定义。
6. 对不可复现的外部 LLM 响应保存 provider、model、参数、提示模板版本、工具证据和结构化结果；敏感原文按策略脱敏。

### 验收

- 同一 `run_id` 在固定数据快照下重跑，核心指标在约定容差内一致。
- 修改任一配置、数据分区或代码 SHA 会产生不同指纹。
- API 返回的交易建议可追溯到原始数据、计算步骤、模型/策略版本和风险门禁。
- 点时测试明确证明未来修订数据不会泄漏到历史运行。

### 风险与回滚

- 迁移先增加 nullable 字段并双写，再回填和收紧约束；禁止一次性破坏旧记录。
- 哈希和快照可能增加存储/计算成本，必须先给容量估算。

## Phase 2：回测与验证可信度升级（P0）

### 目标

将“策略能跑”升级为“研究结果足以支持模拟决策”。

### 设计与实施

1. 建立唯一可信执行语义：信号产生时间、最早可成交时间、价格选择、部分成交、拒单、涨跌停和停牌。
2. 统一 Instrument Specification：乘数、最小变动、手续费固定/比例、保证金、交易时段、到期和换月。
3. 将滑点从常数升级为可插拔但默认简单的模型：spread、成交量参与率和压力情景；不为单一场景过度抽象。
4. 对时间序列验证加入 purging/embargo；对多策略/多参数搜索加入 multiple-testing 纠偏。
5. 输出稳健性报告：分市场状态、分年份、分品种、成本倍数、延迟、参数扰动、缺失数据与极端行情。
6. 定义晋升最小样本和置信标准；样本不足必须返回“证据不足”，不能用 Infinity/NaN 或虚假高置信度代替。
7. 增加基准策略（buy-and-hold、简单趋势、随机/置换基准）和反事实对照。

### 验收

- 所有回测订单都证明没有同 bar 偷看和成交。
- 手续费、保证金、乘数和换月有黄金用例测试。
- 成本 2x、延迟 1 bar、参数小扰动后仍满足预定义下限，才允许进入 Challenger。
- 报告包含样本外指标、置信区间、最大回撤、尾部风险、成交容量和拒绝原因。
- 至少一组故意含未来函数的测试策略会被自动检测或验收测试击败。

## Phase 3：信号结果闭环与组合级决策（P1）

### 目标

从单个信号“看起来合理”升级到可校准、可比较、受组合约束的决策。

### 设计与实施

1. 为不同品种/周期定义成熟窗口，持续完成 MFE、MAE、净收益、方向命中和校准评估。
2. 建立 calibration dashboard：预测置信区间与实际结果分桶；使用 Brier score、可靠性曲线或适合当前输出的指标。
3. 将信号质量分数分解为可解释维度，并记录版本；权重变化必须可回测。
4. 组合候选选择同时考虑相关性、风险预算、流动性、保证金、集中度、品种族群和已有持仓。
5. 建立 Champion/Challenger shadow evaluation，不自动给真实资金权限。
6. 对数据漂移、表现衰减和成本恶化产生“降级/暂停建议”，而非自动重训后直接替换。

### 验收

- 每个置信度档位都有最小样本要求和实际校准误差。
- 同方向高相关候选不会被当作独立机会重复放大。
- 任一组合建议都附带边际风险贡献、压力损失和阻断原因。
- 策略降级、暂停、恢复和人工批准均可审计。

## Phase 4：运行可靠性、可观测性与灾备（P1）

### 目标

让系统在任务失败、重启、数据库异常和数据源波动时可诊断、可恢复。

### 设计与实施

1. 建立统一运行指标：API latency/error、Celery queue age、任务成功率、lease 过期、数据新鲜度、数据源熔断、DB pool、Agent 成本和信号成熟积压。
2. 使用低基数标签；`symbol`、`run_id` 等高基数信息留在日志/查询，不直接作为 Prometheus label。
3. 日志统一关联 `request_id`、`task_id`、`run_id`；敏感字段结构化脱敏。
4. 定义 SLO 和告警：数据新鲜度、关键任务延迟、API 可用性、备份年龄和恢复演练状态。
5. PostgreSQL 建立自动备份、异机/对象存储副本、校验、保留策略和定期恢复演练。
6. 明确 RPO/RTO；提供演练脚本和证据，不把“有 pg_dump 命令”视为灾备完成。
7. 为 Celery 定义幂等键、最大重试、退避、死信/失败队列和人工重放流程。

### 验收

- 模拟数据源失败、Worker 被杀、任务重复投递、DB 短暂不可用时，系统不产生重复关键记录并能恢复。
- 仪表盘能在 5 分钟内回答“哪里坏了、影响什么、是否在恢复”。
- 从最新备份恢复到隔离数据库并通过迁移、行数、约束和关键查询校验。
- 恢复结果满足明确 RPO/RTO，演练日志可审计。

---

## Phase 5：安全、LLM 治理与供应链（P1）

### 目标

降低私有系统中的凭据、越权、提示注入和依赖风险。

### 设计与实施

1. 梳理 Web 管理员、外部 Agent、只读研究、审批者权限矩阵；默认拒绝。
2. Agent 工具调用采用 allowlist、结构化参数、输入验证、超时、预算和审计；禁止 LLM 自由拼接 SQL/命令。
3. 对新闻、网页和用户文本视为不可信内容，防止 prompt injection 改写系统规则或调用高权限工具。
4. 提供 LLM 成本上限、provider 熔断、超时降级和 PII/凭据脱敏。
5. CI 增加 secret scanning、依赖漏洞扫描、容器扫描和 SBOM；扫描结果有明确阻断级别。
6. 设计本机 Git 凭据迁移建议（credential manager 或 SSH），但不得未经用户批准修改当前 remote。

### 验收

- 未授权 principal 无法访问 Agent 写入/审批接口。
- 恶意新闻文本和用户提示不能改变工具权限、读取密钥或绕过交易门禁。
- 日志、错误响应、Agent traces 和导出文件中不出现密钥。
- 高危依赖/容器漏洞和提交中的新密钥能阻断 CI。

---

## Phase 6：前端决策工作台与解释体验（P2）

### 目标

减少信息堆叠，让用户更快判断“是否可信、为什么、风险是什么、下一步做什么”。

### 设计与实施

1. 以任务流重组 Agent 工作台：研究输入 → 数据质量 → 多维证据 → 回测/压力 → 风险门禁 → 人工决策 → 结果跟踪。
2. 每个建议固定显示：方向、净收益假设、置信度校准、证据、反证、数据时间、风险阻断、运行 ID。
3. 关键动作使用显式确认和影响预览；高风险动作不能只靠颜色区分。
4. 增加 stale data、partial failure、证据不足和降级模式的明显状态。
5. 使用真实浏览器做关键路径、响应式、键盘、对比度和错误态验证。

### 验收

- 用户能在一个主流程内回答：数据新不新、结果能否复现、成本后是否有效、最坏会怎样、为什么被阻断。
- 关键页面满足基础 WCAG 2.1 AA 要求。
- API 部分失败时保留成功结果并明确局部失败，不显示虚假“全部成功”。
- 关键路径有浏览器级自动化测试和截图基线。

---

## Phase 7：性能与容量治理（P2，必须先测量）

### 目标

只优化被测量证明的瓶颈，避免无依据重构。

### 设计与实施

1. 建立代表性 workload：K 线查询、横截面构建、Alpha101、回测、Agent 任务、前端大表。
2. 记录 p50/p95/p99、内存、DB 查询计划、缓存命中率和队列等待。
3. 优先优化查询索引、批处理、分页、增量计算和缓存失效；最后才考虑新基础设施。
4. 为 PostgreSQL 表增长、信号观察、Agent 事件和日志制定保留/归档策略。

### 验收

- 每项优化都有前后基准和统计稳定性说明。
- 不接受仅凭单次运行的性能结论。
- 性能优化不得改变点时语义、数值精度和风险门禁。

---

## 6. 建议优先不做的事项

在 P0/P1 完成前，以下事项默认不立项：

1. 新增更多 LLM provider、Agent 角色或“专家人格”。
2. 新增更多未经严格样本外验证的策略、因子或深度学习模型。
3. 微服务化、Kubernetes、Kafka、向量数据库或事件溯源全量重写。
4. 自动实盘执行、自动 Champion 晋升或无人审批资金分配。
5. 为展示效果增加 3D 大屏、复杂动画或与决策无关的可视化。
6. 在没有真实容量瓶颈前更换 PostgreSQL、Celery 或前端框架。

理由：当前系统的边际价值主要来自可信度、复现性、治理和运维，而不是继续扩充功能数量。

## 7. 实施规范

## 7.1 每个任务的标准模板

后续 GPT 必须将每个 Phase 拆成单个可审查任务，每项尽量不超过约 5 个文件：

```markdown
### TASK-X.Y 标题

**目的**：解决什么可验证问题。
**现状证据**：代码、测试、日志或数据证据。
**范围内**：明确文件/模块和行为。
**范围外**：本任务明确不做什么。
**设计**：接口、数据结构、状态转换、失败语义。
**迁移**：兼容、回填、双写、弃用步骤。
**安全与风险**：权限、敏感数据、交易风险。
**测试先行**：先新增哪些失败测试。
**实施步骤**：按依赖顺序的小步修改。
**验收命令**：精确到可复制命令。
**可观测性**：日志、指标、告警或审计事件。
**回滚**：代码和数据分别如何恢复。
**完成定义**：可客观判断的通过条件。
```

## 7.2 数据库变更规范

1. 默认使用 expand → migrate/backfill → contract。
2. 大表 DDL 必须评估锁、时长、磁盘和回滚。
3. 迁移必须同时验证全新数据库和历史数据库升级路径。
4. destructive migration 必须有备份恢复演练和用户批准。
5. API 与 Worker 在滚动升级期间必须兼容新旧 schema。

## 7.3 API 与前端规范

1. 先定义请求、响应、错误码、权限和幂等语义，再实现。
2. JSON 不允许输出 NaN/Infinity；证据不足使用有限值/null 与明确原因。
3. 长任务返回任务 ID，不在 HTTP 请求中同步阻塞。
4. 前端必须覆盖 loading、empty、partial、stale、error、permission denied 状态。
5. 破坏性 API 变更必须版本化或提供迁移窗口。

## 7.4 量化与 ML 规范

1. 所有特征声明信息可用时间，禁止按最终修订值回填历史。
2. 数据切分按时间和实体泄漏风险设计，不能随机打散替代时序验证。
3. 报告同时给净收益、回撤、尾部、容量、换手、成本敏感性和样本量。
4. 模型/参数选择与最终评估数据严格隔离。
5. LLM 输出不能作为无标签真值训练交易模型。

---

## 8. 全局验收与发布门槛

每个 Phase 除自身验收外，还必须满足：

### 8.1 自动化质量门槛

- 后端相关单元和集成测试通过。
- 前端 TypeScript、lint、route check、build 通过。
- Alembic fresh install 与 upgrade path 通过；涉及数据库时验证 downgrade/恢复策略。
- Agent release readiness 通过。
- 新行为有回归测试；禁止仅更新快照让测试变绿。
- 覆盖率门槛由 Phase 0 基线后确定，优先对关键域设门槛，不追求无意义全局百分比。

### 8.2 交易安全门槛

- 任何 live broker/CTP adapter 保持不存在或禁用。
- 人工审批不能被后台任务、LLM 或管理员普通操作绕过。
- 交易成本、保证金和风险阻断不可通过缺省值静默关闭。
- 证据不足、数据过期和部分失败必须 fail closed。

### 8.3 运行发布门槛

- 迁移前备份已验证可恢复。
- 发布有 canary/灰度或最小影响步骤，有明确回滚命令。
- 指标和日志能验证新功能是否正常。
- 发布后执行 smoke test，并对任务积压、错误率和数据新鲜度观察一个约定窗口。

## 9. 专家模型最终输出格式

专家评审结果请保存为新的 Markdown，不要覆盖本文件，并严格按以下结构输出：

1. **Executive Summary**：最多 10 条结论。
2. **Verified Current State**：逐条证据和置信度。
3. **Critical Findings**：P0/P1/P2，包含影响、概率、证据和不修后果。
4. **Keep / Improve / Freeze / Retire Candidates**：模块级建议及理由。
5. **Target Architecture**：仅描述必要变化，包含数据流和信任边界图。
6. **Detailed Phase Plan**：每阶段任务、依赖、文件范围、数据迁移、测试、验收和回滚。
7. **Quant Research Review**：数据泄漏、偏差、成本、统计显著性、容量和复现性。
8. **Security & LLM Governance Review**。
9. **Operations & Disaster Recovery Review**。
10. **Open Questions**：必须由用户决定的问题，给推荐选项和代价。
11. **Rejected Ideas**：明确哪些看似高级但当前不值得做。
12. **Implementation Prompt Pack**：为每个任务生成可单独交给 GPT 的实现提示词。

每条建议必须包含：

```text
状态：VERIFIED / REPO-CLAIMED / PROPOSED
优先级：P0 / P1 / P2 / P3
收益：可量化或可观察结果
成本：预计涉及模块、迁移和运行复杂度
风险：失败模式与影响
证据：文件、测试、运行结果或数据
验收：命令/指标/场景
回滚：代码、配置、数据
```

## 11. 用户需要在实施前确认的决策

专家评审后，用户至少需要确认：

1. **未来 6 个月主目标**：研究可信度、稳定运行、策略收益探索，三者排序。
2. **部署目标**：仅本机开发、单台 VPS、还是本机 + VPS；这决定灾备和发布复杂度。
3. **数据预算**：是否购买点时财务、历史分钟线、Level-2 或期权数据；免费源决定能力上限。
4. **LLM 预算与隐私**：允许哪些数据发送给外部 provider，每月成本上限。
5. **保留范围**：哪些实验模块仍有研究价值，哪些可冻结以降低维护成本。
6. **验收强度**：是否愿意为点时数据、恢复演练和浏览器测试投入额外时间。

在这些决策没有确认前，允许执行 Phase 0；Phase 1 及之后不得大规模展开。

## 12. 完成标准

本轮“专家升级规划”完成，不等于全部功能开发完成。规划阶段的完成标准是：

- 专家模型已基于代码证据验证当前状态；
- 用户已确认 Phase 排序和明确不做事项；
- 每个 P0/P1 任务都能独立交给 GPT 执行；
- 每项任务都有失败测试、验收命令、数据迁移和回滚方案；
- 没有泄露密钥，也没有突破模拟交易与人工审批边界；
- 文档可以作为后续升级工作的唯一主计划，并持续更新实际状态。
